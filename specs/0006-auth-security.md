# 0006 — Аутентификация и безопасность

- **Status:** Accepted
- **Issue:** —

## Проблема

Сервис приватный ровно для двух заранее известных людей. Нужен простой, но не дырявый способ аутентификации на `signaling-server`, и понятная модель того, что зашифровано, а что нет.

## Предлагаемое решение

### Аутентификация

- Никакой регистрации/паролей через UI. Каждому из двух пользователей при деплое вручную выдаётся **долгоживущий bearer-токен** (случайная строка ≥32 байт, сгенерированная сервером или через `openssl rand -hex 32`), захардкоженная пара `(user_id, token)` в конфиге сервера (`deploy/.env`, не в git — см. `.gitignore`). Формат — переменная окружения `ASTER_USERS=id:token,id:token` (ровно два пользователя, разные id и токены, токен ≥32 символов); сервер не стартует при невалидной конфигурации. Токены сравниваются за константное время.
- Клиент хранит свой токен в локальной защищённой конфигурации (например через `keyring`/ОС-хранилище секретов, если Tauri-плагин это даёт удобно; иначе — локальный конфиг-файл с правами `600` как fallback для v1).
- Хендшейк — `Hello { protocol_version, auth_token }` (см. `0003`). Сервер сверяет токен с конфигом, отклоняет несовпадающие (`Rejected`).
- Ровно два допустимых `user_id`. Сервер отклоняет третье соединение с любым валидным на вид, но неизвестным токеном, и не даёт двум соединениям с одним `user_id` работать одновременно (новое соединение вытесняет старое — один пользователь = одна активная сессия).

### Транспортная безопасность

- WebSocket только по WSS (TLS), терминация TLS — на `Caddy` (reverse proxy перед `signaling-server`), сертификат — Let's Encrypt автоматически через Caddy.
- Голосовой трафик — DTLS/SRTP, встроено в WebRTC, обязательно (не opt-out).
- TURN (`coturn`) — тоже за TLS/DTLS где возможно (`turns:`), с собственными credentials (можно static-auth-secret coturn, ротируемый независимо от auth-токенов приложения).

### Что не шифруется отдельно (v1)

- Текстовые сообщения не имеют end-to-end шифрования поверх TLS в v1 — сервер технически может их прочитать в момент релея (но не хранит после доставки, кроме короткой in-memory очереди офлайн-сообщений, `0004`). Это принятый компромисс: сервер контролируется теми же двумя людьми, что и клиенты. E2E — возможное будущее расширение, потребует отдельной спеки (обмен ключами и т.п.).

### Секреты и конфигурация

- Все секреты (auth-токены, coturn static-auth-secret) — в `deploy/.env`, никогда не в git (уже покрыто `.gitignore`).
- `deploy/.env.example` — шаблон без реальных значений, коммитится.

## Альтернативы

- **mTLS (клиентские сертификаты)** — надёжнее, но избыточная сложность (выпуск/ротация сертификатов) для двух пользователей и токена, который и так живёт в приватном канале деплоя. Можно пересмотреть, если понадобится.
- **OAuth/внешний identity provider** — явно избыточно для двух захардкоженных пользователей.

## Затронутые компоненты

- `crates/signaling-server` — проверка токена, отказ дублирующим сессиям.
- `crates/client` — хранение токена.
- `deploy/` — `.env.example`, Caddyfile, coturn config.

## Открытые вопросы

- Использовать ли `keyring` crate для хранения токена в клиенте сразу в v1, или начать с файла с правами `600` и вынести в отдельный issue позже — решить при реализации `crates/client`.

# 0004 — Текстовый чат

- **Status:** Accepted
- **Issue:** #4

## Проблема

Нужен реалтайм текстовый чат 1:1 с историей, при этом сервер по архитектуре (`0002`) не должен становиться хранилищем сообщений, а нагрузка на VPS должна оставаться минимальной. Нужно решить, что происходит, когда получатель офлайн.

## Предлагаемое решение

### Онлайн-случай (оба клиента подключены)

Прямой релей через `signaling-server` (см. `0003`): отправитель шлёт `ChatMessage`, сервер пересылает его подключённому получателю и присылает `ChatDelivered` отправителю. Задержка — доли секунды, сервер ничего не пишет на диск.

### Офлайн-случай (получатель не подключён)

Сервер держит **небольшую очередь недоставленных сообщений в памяти** (не БД) на подключённого пользователя, с TTL (например 7 дней) и разумным лимитом (например 500 сообщений на пользователя). При переподключении получателя очередь его сообщений доставляется и очищается. Отправитель получает `ChatQueued` сразу, а `ChatDelivered` — в момент фактической доставки из очереди, если сам в этот момент онлайн (если офлайн — подтверждение теряется, сообщение остаётся у него в статусе Queued). При переполнении очереди отправитель получает `Error { QueueFull }`, сообщение отбрасывается. Если сервер перезапускается — недоставленные сообщения теряются (это компромисс: не хотим тащить постоянное хранилище и модель бэкапов ради двух пользователей; сообщения, критичные для доставки, дублируются пользователем вручную, как в любом мессенджере при потере связи).

Если через некоторое время (v1) это окажется недостаточным — можно перейти на персистентную очередь (sqlite-файл рядом с сервером), это не меняет протокол, только реализацию сервера.

### Локальная история

Каждый клиент хранит полную историю переписки в локальном SQLite (`crates/client`), включая свои же отправленные сообщения (пишутся в БД сразу при отправке, статус обновляется по `ChatDelivered`). История не синхронизируется между устройствами одного пользователя в v1 (один пользователь = одна установка клиента).

### UI-поведение

- Статусы сообщения: `Sending -> Sent (delivered to server) -> Delivered (получатель online, доставлено) / Queued (получатель offline)`.
- Индикатор presence второго пользователя (online/offline) — из `PeerStatus`.

## Альтернативы

- **Постоянное хранилище на сервере (БД)** — отклонено для v1: усложняет деплой (миграции, бэкапы) ради небольшого выигрыша при и так редких офлайн-окнах между двумя людьми. Оставлено как путь эскалации.
- **Синхронизация истории через сервер между устройствами** — вне скоупа v1 (`0001`, один клиент на пользователя).

## Затронутые компоненты

- `crates/signaling-server` — in-memory очередь недоставленных сообщений.
- `crates/client` — SQLite-схема сообщений, UI статусов.
- `crates/protocol` — уже покрыто `0003`.

## Открытые вопросы

- Нужно ли шифровать локальную SQLite базу на клиенте (на случай кражи ноутбука)? Возможное будущее расширение, не блокирует v1.

# 0002 — Архитектура системы

- **Status:** Accepted
- **Issue:** —

## Проблема

Нужна архитектура, которая: минимизирует нагрузку/трафик на дешёвом VPS, работает через NAT для обоих пользователей, и достаточно проста для поддержки двумя людьми в свободное время.

## Предлагаемое решение

### Топология

```
   Client A (Tauri)                                Client B (Tauri)
   ┌───────────────┐        WebSocket (WSS)        ┌───────────────┐
   │ Leptos UI     │◄─────────────┐   ┌────────────►│ Leptos UI     │
   │ WebRTC peer   │              │   │              │ WebRTC peer   │
   │ SQLite (hist.)│              │   │              │ SQLite (hist.)│
   └───────┬───────┘              │   │              └───────┬───────┘
           │                ┌─────▼───▼─────┐                │
           │                │ signaling-srv │                │
           │                │  (axum, VPS)  │                │
           │                └─────┬─────────┘                │
           │                      │ TURN (coturn, fallback)   │
           └──────────────WebRTC P2P (audio, DTLS/SRTP)───────┘
```

- **Сервер сигнализации** — единственный постоянно работающий серверный компонент помимо TURN. Держит два WebSocket-соединения (по одному на пользователя), релеит:
  - SDP offer/answer, ICE candidates (для установления WebRTC-сессии);
  - текстовые чат-сообщения (когда оба онлайн — прямой релей; см. `0004` про офлайн-случай);
  - presence (кто сейчас онлайн).
  - Сервер **не** декодирует и не хранит голосовой трафик — только сигналинг. Это держит нагрузку на VPS минимальной.
- **Голос** — P2P WebRTC между клиентами напрямую (звук идёт по кратчайшему пути в сети, не через VPS), с `coturn` на том же VPS как relay-фолбэк, если прямое P2P-соединение не устанавливается (симметричный NAT и т.п.).
- **Текстовый чат** — тоже через WebSocket сигналинга (не отдельный канал), т.к. объём трафика тривиален и не стоит городить второй транспорт. История — локально у каждого клиента в SQLite; сервер не персистит сообщения (см. открытые вопросы).

### Почему не SFU/MCU

Для 1:1 голосового звонка SFU не даёт преимущества (он нужен для >2 участников), а P2P с TURN-фолбэком даёт: меньше нагрузки на VPS, меньше задержка (прямой путь), меньше кода для поддержки. Если в будущем понадобятся групповые звонки — потребуется отдельная спека и, вероятно, SFU (`webrtc-rs` + `str0m` или медиасервер).

### Crates

| Crate | Назначение | Ключевые зависимости |
|---|---|---|
| `protocol` | Общие типы сообщений (сигналинг + чат), версия протокола | `serde` |
| `signaling-server` | WS-сервер, relay, presence, auth | `axum`, `tokio-tungstenite`, `tokio` |
| `client` | Tauri app: UI, WebRTC peer, локальная история | `tauri`, `leptos`, `webrtc-rs`, `rusqlite`/`sqlx` |

## Альтернативы

- **Полностью P2P без сервера** (например, через DHT/mDNS-подобное обнаружение) — отклонено: нужен NAT traversal и предсказуемый способ найти собеседника, когда оба за NAT; centralized signaling проще и дешевле в реализации для двух известных заранее пользователей.
- **Всё через сервер (relay всего аудио)** — отклонено на этом этапе: больше нагрузки/трафика на дешёвый VPS, хотя проще NAT traversal. Можно вернуться к этому, если TURN-фолбэк окажется недостаточным на практике.

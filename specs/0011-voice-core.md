# 0011 — Голосовые звонки в ядре клиента

- **Status:** Accepted
- **Issue:** #46

## Проблема

`0005` описывает звонок на уровне протокола и UX, `0009` и `0010` — ядро соединения и чата. Для реализации голоса (#7) не хватает решений:

- какие библиотеки брать (WebRTC, Opus, аудио-I/O) с учётом системных зависимостей;
- машина состояний звонка с таймаутами и одновременным вызовом (glare);
- что делать при обрыве сигналинга и ICE;
- звуковой тракт: кадры, jitter, VAD;
- контракт команд и событий для UI звонка (`0008`, шаг 5);
- как тестировать без реальных аудиоустройств.

## Предлагаемое решение

### Библиотеки

| Задача | Crate | Почему |
|---|---|---|
| WebRTC (ICE, DTLS-SRTP, RTP) | `webrtc` 0.20.x (webrtc-rs, стабильная ветка, не `-rc`) | async на tokio, как всё ядро; Opus-трек из коробки |
| Opus | `opus-pure` 0.2 | чистый Rust: ни `libopus-dev`, ни `cmake`; энкодер и декодер, SILK/CELT |
| Аудиоустройства | `cpal` 0.18 | кроссплатформенный захват и воспроизведение |

- `cpal` стоит за cargo-фичей `audio-device` (включена по умолчанию). На Linux ей нужны заголовки ALSA: `alsa-lib-devel` (Fedora) / `libasound2-dev` (Debian/Ubuntu, уже в CI). Без фичи клиент собирается и работает, звонки устанавливаются, но звука нет — это режим для разработки и тестов.
- Кодек спрятан за внутренним интерфейсом `encode(frame) -> packet` / `decode(Option<packet>) -> frame`. `opus-pure` молодой crate: если он подведёт, замена на `libopus` через `audiopus` затронет только этот модуль.

### Звуковой тракт

Внутренний формат — 48 kHz, моно, `f32`, кадр 20 мс = 960 сэмплов.

**Захват:** `cpal` input (конфиг 48 kHz, если устройство умеет, иначе линейный ресемплинг) → даунмикс в моно → накопитель кадров → гейт (mute/VAD) → Opus (`VOIP`, 32 kbps, in-band FEC, ожидаемые потери 10%) → `TrackLocalStaticSample`.

При mute или тишине по VAD кодируется тишина, а не пропускается кадр: поток RTP остаётся ровным, у собеседника не срабатывает маскировка потерь.

**Воспроизведение:** удалённый трек → RTP → Opus-декодер → jitter-буфер → `cpal` output.

- **Jitter-буфер:** стартует после накопления 3 кадров (60 мс), максимум 10 кадров (при переполнении отбрасываются старые).
- **Потери:** пропуск номера RTP-последовательности до 3 пакетов → столько же вызовов PLC декодера; больший разрыв — просто продолжаем. Опоздавшие пакеты отбрасываются.
- **Опустошение буфера:** один кадр PLC, дальше тишина до повторного накопления 3 кадров.

**VAD:** RMS кадра в dBFS; «говорит», если выше −45 dBFS, с удержанием 300 мс. Используется для гейта своего микрофона и для индикаторов «говорит» (свой — по захвату, собеседника — по декодированному звуку).

**Эхоподавления и шумоподавления в v1 нет** (webrtc-rs их не даёт). Известное ограничение: пользоваться наушниками. Push-to-talk (`0005`) и выбор устройств — отдельные issue, в v1 устройства по умолчанию.

### Сигналинг звонка

Используются существующие `SignalPayload` (`0003`), протокол не меняется.

- **Инициатор:** создаёт `RTCPeerConnection` с `ice_servers` из последнего `Welcome` (`0009`) и локальным аудиотреком, отправляет `Offer`, дальше trickle `IceCandidate`.
- **Получатель:** `Offer` вне звонка = входящий вызов. Offer сохраняется, ранние `IceCandidate` буферизуются до `set_remote_description`. Принятие → `Answer`, отклонение → `CallEnd`.
- **Glare** (оба нажали «позвонить» одновременно, `Offer` пришёл в состоянии `calling`): звонящим остаётся сторона, чей Offer имеет меньший session id из строки `o=` SDP. Оба клиента видят одни и те же два числа, поэтому решение согласовано. `user_id` для этого не годится: клиент не знает `user_id` собеседника. Проигравший закрывает свой `RTCPeerConnection` и сразу принимает чужой Offer — оба хотели разговаривать, звонок без лишнего `ringing`.
- `CallEnd` в любом активном состоянии завершает звонок.

### Машина состояний

```
idle ──start_call──► calling ──Answer──► connecting ──ICE connected──► connected
idle ──Offer───────► ringing ──accept──► connecting
любое активное ──hang_up/decline/CallEnd/таймаут/ошибка──► ended{reason} ──► idle
```

| Событие | Реакция | `reason` |
|---|---|---|
| `hang_up` / `decline_call` | `CallEnd` собеседнику | `hangup` / `declined` |
| `CallEnd` в `calling` | — | `declined` |
| `CallEnd` в `ringing` | — | `cancelled` |
| `CallEnd` в `connecting`/`connected` | — | `remote_hangup` |
| 30 с в `calling`/`ringing` | `CallEnd` | `timeout` |
| 20 с в `connecting` без ICE `connected` | `CallEnd` | `failed` |
| ICE `failed`, или `disconnected` дольше 10 с | `CallEnd` (best effort) | `connection_lost` |
| `PeerStatus { online: false }` или `Error { peer_offline }` до `connected` | — | `peer_offline` |
| сигналинг ушёл из `connected` до установления медиа | — | `connection_lost` |
| `failed { session_replaced }` | — | `connection_lost` |
| ошибка WebRTC при создании offer/answer | `CallEnd` | `failed` |

После установления медиа (`connected`) обрыв сигналинга и `PeerStatus { online: false }` звонок **не** завершают: медиа идёт P2P или через TURN мимо сигналинг-сервера. Решает только ICE.

`ended` — мгновенное состояние: ядро эмитит `ended { reason }` и сразу `idle`. Показ итога звонка — забота UI.

`start_call` разрешён только в `idle` при `connected`-сигналинге и онлайн-собеседнике, `accept_call`/`decline_call` — только в `ringing`, `hang_up` — в любом активном состоянии.

Ошибка аудиоустройства (нет микрофона, устройство пропало) звонок не завершает: эмитится `call-audio-error`, звонок продолжается без захвата или без воспроизведения.

### Команды Tauri

| Команда | Аргументы | Результат |
|---|---|---|
| `start_call` | — | `()` |
| `accept_call` | — | `()` |
| `decline_call` | — | `()` |
| `hang_up` | — | `()` |
| `set_muted` | `{ muted: bool }` | `()` |
| `call_state` | — | `CallState` |

Ошибки: `invalid_state` (команда не подходит к текущему состоянию), `not_connected`, `peer_offline`.

### События Tauri

| Событие | Payload |
|---|---|
| `call-state` | `CallState` |
| `call-audio` | `{ muted: bool, local_speaking: bool, remote_speaking: bool }` — при изменении любого поля во время звонка |
| `call-audio-error` | `{ direction: "capture" \| "playback", message: string }` |

```json
{ "state": "idle" }
{ "state": "calling" }
{ "state": "ringing" }
{ "state": "connecting" }
{ "state": "connected", "since": 1726500000000 }
{ "state": "ended", "reason": "remote_hangup" }
```

`since` — мс, момент перехода в `connected` (для таймера в UI). Незнакомый `reason` UI показывает общим текстом (как `other` в `0009`).

### Устройство модуля

`crates/client/src-tauri/src/core/voice/`:

- `call` — актор звонка: машина состояний, `RTCPeerConnection`, подписка на события сигналинга, отправка `Signal` через `SignalingHandle`;
- `media` — чистые функции и структуры звукового тракта: накопитель кадров, VAD, jitter-буфер с PLC, обёртка кодека. Без I/O, покрываются unit-тестами;
- `audio` — трейт `AudioBackend` (запуск захвата с колбэком на кадры, запуск воспроизведения с источником кадров). Реализации: `cpal` (фича `audio-device`), `null` (без звука) и тестовая, которая подаёт заданный сигнал и собирает выход.

### Тестирование

- **Unit (`media`):** синус 440 Гц через encode → decode сохраняет частоту и уровень; VAD на тишине и речи, удержание; jitter-буфер: старт после 3 кадров, переполнение, PLC на разрыв последовательности.
- **Интеграционные** (два ядра, настоящий `signaling-server`, настоящий webrtc-rs через loopback, тестовый аудио-бэкенд):
  - вызов → принятие → `connected` у обоих → синус alice слышен у bob, а синус bob — у alice (энергия на нужной частоте);
  - mute → у собеседника тишина, `remote_speaking` гаснет;
  - отклонение, отмена звонящим, таймаут, glare, собеседник офлайн, hang_up с каждой стороны.

## Альтернативы

- **`str0m`** (sans-IO WebRTC) — отклонено для v1: цикл UDP-сокетов, таймеров и ICE пришлось бы писать самим. webrtc-rs даёт это готовым и уже на tokio.
- **`libopus` через `audiopus`/`opus`** — отклонено для v1: нужны `libopus-dev` или `cmake` на каждой машине разработчика. Интерфейс кодека оставляет путь назад.
- **Звук через webview (`getUserMedia` + браузерный WebRTC)** — отклонено ещё в `0005`/`0009`: WebRTC в Rust-ядре. Кроме того, WebKitGTK на Linux поддерживает WebRTC нестабильно.
